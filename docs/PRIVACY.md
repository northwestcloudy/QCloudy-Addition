# QCloudy Dungeon quick-view and market privacy

This document covers QCA's Dungeon Player Quick View and Shard Planner market requests. It does not replace the general client/rules boundary in `COMPLIANCE.md`.

## When a request happens

QCA requests Dungeon data only after the client receives the exact Dungeon Finder message that a new player joined the dungeon group, Dungeon Quick View is enabled, and the session is authoritatively on Hypixel SkyBlock. It queries that newcomer only. To attach the correct floor before instance queueing, it may read the local player's own entry in an already-open Party Finder menu, but only when the same menu exposes the delist control; it does not request or inspect another party's profile, poll Party Finder, click the menu, or create player history. If the separately confirmed, default-off admission master and at least one rule for that own F1–F7/M1–M7 listing are enabled, QCA asks the official Hypixel Mod API for one fresh PartyInfo snapshot and, only after a confirmed FAIL, one second final snapshot—at most two PartyInfo requests per admission. Entrance and scoreboard-only floor detection never start an automatic action decision. The Shard Planner requests its bounded price snapshot when its price data is explicitly loaded.

## Data sent by the mod

The destination is fixed to `https://api.qcloudy.net`. The request contains the joining Minecraft player name and, when the own Party Finder entry or local scoreboard exposes one, the advertised/queued floor ID. The server and ordinary network infrastructure can observe the connecting IP address and QCA User-Agent. The mod does not send a Minecraft session token, Microsoft credentials, Hypixel API key, current server address, mod list, chat history, coordinates, inventory upload, cookie, or telemetry/device identifier. The official PartyInfo request stays on the Minecraft/Hypixel Mod API connection; its UUID/role map is not uploaded to QCloudy.

Profile cards retain `CLICK HERE TO KICK THE PLAYER OUT`; a physical click sends `/party kick <validated player>` to the Minecraft server through the normal chat click event. Separately, an explicitly confirmed admission configuration may send `party kick <validated newcomer>` after a confirmed FAIL. F1–F7 and M1–M7 each own independent settings for minimum floor completions, duplicate class, maximum fastest completion, minimum average Secrets, minimum historical-highest Magical Power, Wither Blade, Terminator, Golden Dragon, and Ender Dragon; every rule and the automatic-action master default off, and Entrance has no rules. Players already present at queue creation and ordinary/manual party joins are trusted, used only as DUPE class context, and never queried or kicked by this feature. PASS prints only Profile. UNKNOWN prints Profile plus reasons and never kicks. FAIL prints every confirmed failure and concrete concurrent evidence error first, then sends the command in the same client-thread decision turn only if a fresh official PartyInfo snapshot still proves local-leader role and target UUID membership and the own listing, floor, rules, session/world, and one-shot action remain unchanged. The command is sent to the Minecraft server, not QCloudy; QCA does not claim that it succeeded.

## Processing and retention

The source QCloudy service resolves the joining name and fetches the corresponding Hypixel player and SkyBlock Profiles with a server-side application key. It selects the active profile (or latest visible profile), projects only the fields needed for the chat card and requirements evidence, and returns a bounded response. Name/UUID data is cached for 72 hours with a 15-minute negative cache. Dungeon player and Profile data are fresh for two minutes; a prior value may be used for at most ten minutes only after a technical upstream failure. Private, missing, stale, identity/floor-mismatched, uncertain-Profile, and incomplete inventory/pet results remain UNKNOWN and are not converted to zero. A network/transport failure cannot authorize a command.

Requirements evidence is tied to the resolved UUID, selected Profile, requested/returned floor, freshness, and source coverage. Version 2 divides the selected Profile's `member.dungeons.secrets` by only that Profile's explicit F1–F7/M1–M7 completions, excluding Entrance, aggregate totals, account achievements, and blood-mob compensation. Missing/malformed data or zero runs stays UNKNOWN, while confirmed Mage newcomers skip the rule. The Alpha 9 backend source is not deployed by the mod build and the complete flow has not been tested on an authenticated live Hypixel session. A version-1 response keeps average Secrets UNKNOWN; a response without supported evidence remains display-only/UNKNOWN.

The playable mod coalesces identical in-flight requests and keeps successful quick-view results in process memory for 60 seconds. It cancels pending work when the client session changes and does not write remote player snapshots into `config/qcloudy_addition.json`.

Bazaar snapshots refresh about every 60 seconds and have a ten-minute technical stale limit. Active-auction snapshots refresh about every two minutes and have a fifteen-minute stale limit. Deduplicated ended-auction market samples are retained for about 30 days; they are market transactions, not QCA player lookup history. SQLite stores those market samples only, not Dungeon quick views. Production templates disable Nginx and Uvicorn access logs so names in request paths are not retained as browsing history.

## Security boundary

The Hypixel application key remains in the server environment and is never packaged in the JAR or returned to a client. The service exposes fixed transformed routes, not an arbitrary Hypixel proxy. The mod requires HTTPS, rejects redirects and origin changes, and bounds request time and response size. Operational logs may contain bounded technical status but must not contain the player query, API key, request body, or complete upstream response. Automatic-action guards and local PartyInfo do not weaken these HTTP bounds or add a QCloudy telemetry path.
